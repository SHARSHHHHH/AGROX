# Sustainable Agriculture Advisory Platform

AI-assisted advisory for farmers in Madhya Pradesh. Voice-first, three
languages, and every number the farmer acts on is computed by deterministic
rules rather than generated by a model.

**233 backend tests + i18n coverage checks passing. Frontend builds clean.**

## Recent fixes

| Symptom | Cause | Fix |
|---|---|---|
| "What should I grow" very slow | One mandi API call **per crop**, each with 3 retries | One bulk call, grouped locally. 54s -> 2.3s in tests |
| Every crop showed the same price | data.gov.in silently ignores a filter it cannot apply and returns the **unfiltered** feed | Client-side re-verification; a tomato query can never return carrot |
| "Server busy" constantly | Same N-calls-per-request problem hitting the rate limit | 1 call instead of 15 |
| Only 4-5 crops listed | `MP_CROPS` had 5 entries; API returned only top 5 | 15 crops, all returned |
| Voice heard only English | `recog.lang` is read once at `start()`; changing language never restarted it | Recognition restarts on language change |
| Dictation garbled/doubled | Stale base text re-applied on restart | Dictation guard + de-duplicating compose |
| GPS did nothing | Coordinates were stored but never resolved | Offline MP district table + OSM fallback, auto-fills state/district |
| ROI always "not worth it" | Read the **mock** price service, which ROI correctly refuses for money, so revenue was always zero | Reads the real AGMARKNET feed |

## The architecture in one line

```
REAL DATA (sensors, weather, data.gov.in) + RULES + MODELS
        -> ADVISORY ENGINE (deterministic)
        -> LLM (explains only)
        -> farmer, in their language
```

The LLM never decides. By the time it is called, the crop is already ranked,
the severity already graded, the price already fetched. It writes sentences.

Enforced structurally, not by prompt wording:

- `VisionObservation` has no field where a treatment could be expressed
- `evaluate_pump_request()` has no parameter to override a safety block
- `advisor.grounded_facts()` ends with "do NOT reorder"
- `mandi_price.grounded_facts()` says "Do NOT state any price figure" when data is missing

## Quick start (recommended)

```bash
# Windows
start.bat

# macOS / Linux
./start.sh
```

These pick a free port, start the backend on it, **write
`frontend/.env.local` so the frontend proxies to the same port**, and launch
both. Port mismatch is the single most common cause of a blank dashboard.

If something is wrong:

```bash
cd backend && python scripts/doctor.py
```

It checks whether the backend is listening, whether the frontend proxy points
at the right port, whether the database is seeded, and whether the configured
providers are installed.


Copy `.env.example` to `.env` and fill in. **Never commit `.env`.**

```bash
HF_VISION_MODEL=Kathir56/plant-disease-tamilnadu
HF_VISION_MIN_CONFIDENCE=0.60
```

`DATA_GOV_API_KEY` is read **only** inside `app/services/mandi_price.py`,
server side. The React app calls `/api/market-prices`; the key never crosses
that boundary. A test asserts it never appears in any response body.

## data.gov.in mandi integration

Resource `9ef84268-d588-465a-a308-a864a43d0070` (AGMARKNET, Ministry of
Agriculture). Field names were **verified against a live response**, not
assumed. Three things break a from-memory implementation:

1. **`arrival_date` is `DD/MM/YYYY`**, not ISO. Naive parsing produces an
   invalid month.
2. **The state filter is `filters[state.keyword]`.** District, market and
   commodity are plain names. Using `filters[state]` returns zero rows with no
   error at all.
3. **Spellings are AGMARKNET's, not common usage.** Live data returns
   `"Keralam"`, not Kerala. Soybean is `"Soyabean"`. Chickpea is
   `"Bengal Gram(Gram)(Whole)"`. `STATE_ALIASES` and `COMMODITY_ALIASES` map these.

Also: the API defaults to **XML** — `format=json` is required.

Behaviour: 15-minute cache, retry with backoff on 5xx, no retry on 401/403,
and `empty` (no arrivals reported today) is kept distinct from `unavailable`
(API down) because those need different messages to a farmer.

## Machinery rental marketplace

Farmer-to-farmer equipment hire, with three tabs: **rent**, **give on rent**,
and a **guide** to what machinery a given farm actually needs.

**Distance ranking.** Listings sort by real haversine distance from the
searcher. A listing without GPS falls back to its state centre and is marked
approximate — never presented as exact. Covers all 36 states and UTs.

**Phone numbers are gated.** `contact_phone` never appears in browse results;
those show a masked `98xxxxx210`. The real number is released only through an
authenticated POST to `/contact`, one listing at a time, so the feed cannot be
scraped for numbers in bulk. Every reveal carries a safety note telling the
farmer to agree terms and inspect the machine before paying.

**Illustrations are inline SVG**, a few hundred bytes each, so cards render
instantly with no network. An owner's uploaded photo replaces the illustration
when present.

**The guide is deterministic.** It filters the catalogue by crop and land size:
a 2.5-acre farmer is shown a tractor and rotavator, and explicitly told a
combine harvester and a baler are *not* worth it at that size, with the reason.

## Crop advisory engine

`app/services/advisor.py`. Deterministic and weighted:

| Signal | Weight | Source |
|---|---|---|
| Agronomy (pH, NPK, season, temperature, soil type) | 70% | `crop_suitability.py` |
| Rotation vs previous crop | 18% | `rotation.py` |
| Live market price | 12% | `mandi_price.py` |

Water availability **gates** the agronomy score rather than adding to it — a
high-water crop on rainfed land is not made viable by good soil.

Every input is tagged `SENSOR` / `MANUAL` / `LIVE_API` / `MISSING`, surfaced in
the UI, so the farmer sees what the advice actually rests on. Estimated values
are never presented as measured.

The output field is `advisory_suitability_score`. Never "best crop", never a
yield prediction. The disclaimer says so in every response.

**Rotation is a knowledge layer** (`rotation.py`), not logic buried in a UI
component, so an agronomist can correct it without touching code. Legume then
cereal scores highest: soybean after wheat restores nitrogen, which is the
dominant Madhya Pradesh rotation.

## Onboarding

Five steps, every free-text field voice-enabled, and it **saves as you go** so
a dropped connection loses nothing.

1. Location — GPS offered, manual always works
2. Land — size, category, soil type, irrigation, water source
3. Previous crop — drives rotation scoring
4. Current crop plus **sowing date**
5. Soil test (optional)

`sowing_date` is the important one. With it, lifecycle stage is computed
automatically. Without it, someone has to type their growth stage by hand every
single time.

Nothing is defaulted to a plausible value. An unanswered land size stays empty
rather than becoming "1 acre", because an invented figure silently corrupts
every downstream recommendation.

## Voice and translation

**Three languages ship complete: Hindi, English, Tamil.** Hindi is the default
when the browser locale is not one of the three, and is first in the picker.

Telugu, Kannada and Malayalam were **removed** from the picker. They had login
strings only and fell back to English everywhere else — a half-translated
language is worse than not offering it.

Two translation layers:

- `t()` — UI chrome, 257 keys
- `tv()` — **data values** from the backend: crop names, severity, IPM tiers,
  verdicts. Without this a Tamil page reads "தீவிரம்: MODERATE", which is worse
  than plain English throughout.

Browser Web Speech API, so voice works independently of our backend and on the
login page where no auth token exists. Chrome/Edge/Android supported; Firefox
degrades to typing.

```bash
cd frontend && node tests/i18n.test.mjs
```

Checks key parity across all three languages and scans pages for hardcoded
English. It caught a missed "Village" label during this build.

## Database

SQLite via SQLAlchemy. **Additive auto-migration on startup**
(`db.ensure_schema()`) adds columns that exist in models but not in an older
`agri.db`. Without it, adding a field breaks every query on that table with
"no such column" — which looks exactly like lost data. It only ever ADDs
columns, so it cannot lose anything.

Your database is one file: `backend/agri.db`. It is **not** in the zip. Each
version extracts to its own folder, so carry it forward:

```bash
python scripts/migrate_data.py --backup           # before upgrading
python scripts/migrate_data.py /path/to/old/agri.db
```

## Known limitations

- **EfficientNet-B0 and IP102/YOLO are not integrated.** They do not exist in
  this repo yet. Disease detection currently runs whatever `HF_VISION_MODEL`
  points at; pest detection has no dedicated model.
- **The backend's outbound data.gov.in call is untested from CI** — schema
  verified against live data, transport mocked. The first real call happens on
  your machine.
- **Backend free text is still English.** KB symptom descriptions and IPM step
  wording live as prose in `DISEASE_KB`/`PEST_KB`. The chat answer is
  translated; those stored strings are not.
- **Agronomic reference data is compiled, not validated.** Crop ranges,
  lifecycle timings and rotation rules are representative for Madhya Pradesh.
  Review against JNKVV or RVSKVV package-of-practices before production use.
  Every response carries a disclaimer pointing to the local Krishi Vigyan Kendra.
- **Qwen on CPU takes 15-40 seconds per answer.** Inherent to a local 1.5B
  model without a GPU. Lower `QWEN_MAX_NEW_TOKENS` or switch to Gemini.
